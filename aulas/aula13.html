Diferenciar

SLI mede (razão observada). SLO declara meta sobre o SLI em uma janela. SLA é contrato externo com penalidade.

Escolher

De KPI para SLI bom: percentil > média, "good event" e "valid event" claros, janela explícita versionada.

Orçar

Error budget = 1 menos SLO. Distinguir consumo lento (degradação) de queima aguda (incidente em curso).

Decidir

Com burn rate na mão: ajustar SLO (com ADR), ajustar código (revert e fix) ou aceitar a queima (budget existe pra ser gasto).

Bloco 2, 15 min

SLI, SLO, Error Budget

3 conceitos. 1 slide. Resto da aula aplica em cima do demo.

inteli

A hierarquia em 1 slide

SLI (Indicator)

O que medimos. Razão: good_events / valid_events. Ex.: nº de missões que terminaram em LANDED dividido pelo nº de missões iniciadas.

SLO (Objective)

Meta declarada sobre o SLI em uma janela. Ex.: 95% das missões finalizam em LANDED em janela de 30 dias.

Error Budget

1 menos SLO sobre a janela. Se SLO=95%/30d e tivermos 200 missões, podemos "quebrar" até 10 sem violar.

Burn rate

Velocidade com que o budget é consumido. Burn alta numa janela curta (1h) sinaliza incidente agudo. Burn lenta numa janela longa (30d) sinaliza degradação.

Por que percentil é melhor que média

Média esconde cauda. O p95 captura "os 5% piores", onde mora a dor do usuário. Um valor médio bonito pode conviver com 5% de missões catastróficas.

Exemplo trabalhado: mission_success_rate

slo:
  name: mission_success_rate
  sli:
    good: "missões com terminal_state == LANDED e battery_pct >= 20"
    valid: "missões iniciadas com armed == true"
  objective: 0.95
  window: 30d
  burn_rate_alerts:
    - { window: 1h,  threshold: 14.4 }  # consome 2% do budget em 1h
    - { window: 6h,  threshold: 6.0 }   # multi-window

Por que cada linha está aí

  1. good exclui pousos forçados (battery menor que 20).
  2. valid exclui missões abortadas pelo CI antes do arm.
  3. 30d captura tendência longa; 1h e 6h capturam incidente em curso.
  4. Multi-window: 2 janelas alertam cedo sem alarme falso. ADR-010 detalha os thresholds.
  5. threshold 14.4: derivado de "queimar 2% do budget mensal em 1h".

slos.yaml: 3 SLOs do demo

slos:
  - name: mission_success_rate
    sli:  { good: "terminal_state == LANDED and battery_pct >= 20",
            valid: "armed == true" }
    objective: 0.95
    window: 30d
    burn_rate_alerts:
      - { window: 1h, threshold: 14.4 }
      - { window: 6h, threshold: 6.0 }

  - name: p95_mission_duration
    sli:  { metric: "duration_s", aggregate: "p95",
            valid: "terminal_state == LANDED" }
    objective_max: 180        # segundos
    window: 30d

  - name: rollback_time_p95
    sli:  { metric: "rollback_seconds", aggregate: "p95",
            valid: "incident == true" }
    objective_max: 300
    window: 30d

Anatomia do arquivo

  1. metrics_source: aponta para o mesmo reports/metrics.json que o job mission-test já gera desde A08. Nenhum dado novo.
  2. objective vs objective_max: razão de sucesso quer "no mínimo X"; latência quer "no máximo Y segundos".
  3. 3 SLOs, 3 dimensões: confiabilidade (success), performance (p95), recuperação (rollback).
  4. Versionado em git: mudar SLO vira PR, vira ADR, vira discussão. Não vira chat no Slack.

tools/error_budget.py: o núcleo

# tools/error_budget.py
# history.jsonl é apêndice. A08 vai precisar de update pra escrever lá:
# { "ts": "2026-06-15T10:00:00Z", "success": true, "duration_s": 172, ... }

from datetime import datetime, timedelta, timezone
import json, pathlib

def load_history(path="metrics/history.jsonl"):
    with pathlib.Path(path).open() as f:
        return [json.loads(line) for line in f if line.strip()]

def within(window, runs, now=None):
    now = now or datetime.now(timezone.utc)
    cutoff = now - window
    return [r for r in runs if datetime.fromisoformat(r["ts"]) >= cutoff]

def compute_burn_rate(slo, history, window):
    runs = within(window, history)
    if not runs:
        return 0.0
    failures = sum(1 for r in runs if not r["success"])
    observed_error_rate = failures / len(runs)
    allowed_error_rate = 1.0 - slo["objective"]
    if allowed_error_rate == 0:
        return float("inf") if observed_error_rate > 0 else 0.0
    return observed_error_rate / allowed_error_rate   # burn rate

O que ler aqui

  1. history.jsonl é append-only. 1 linha por mission run. Sem schema rígido.
  2. within(window, ...): filtra runs nas últimas N (1h, 6h, 30d).
  3. burn_rate = observed / allowed: 1.0x significa "queimando exatamente no ritmo do budget". 14.4x é incêndio.
  4. Edge case: SLO 100% (allowed=0) é divisão por zero. Defendido explicitamente.
  5. Testes: history vazio, janela menor que dado disponível, SLO 100%.

Job slo-check + comentário no PR

# .github/workflows/ci.yml
slo-check:
  needs: quality-gates
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - uses: actions/download-artifact@v4
      with: { name: history, path: metrics/ }
    - run: python tools/error_budget.py slos.yaml > slo_report.md
    - uses: marocchino/sticky-pull-request-comment@v2
      with:
        path: slo_report.md
        header: slo-status

## Comentário gerado no PR:

## 📊 SLO Status

| SLO                  | Target  | Current (30d) | Budget    | Burn rate (1h) |
|----------------------|---------|---------------|-----------|----------------|
| mission_success_rate | 95%     | 96.5%         | 30% used  | 0.8x (ok)      |
| p95_mission_duration | ≤ 180s  | 172s          | 60% used  | 1.2x (ok)      |
| rollback_time_p95    | ≤ 300s  | 245s          | 18% used  | 0x   (ok)      |

🟢 Todos os SLOs dentro do budget.

3 escolhas didáticas

  1. needs: quality-gates: roda DEPOIS dos gates de A10. Não substitui, complementa.
  2. Não bloqueia merge: SLO esgotado é sinal pra time, não veto automático. ADR-010 trata.
  3. sticky comment: atualiza o mesmo comentário a cada push. Não vira spam no PR.
  4. Tabela markdown: leitura rápida no PR. Verde/amarelo/vermelho pelo emoji header.

Em duplas. 35 min cronometrados. Discussão guiada começa aos 30 min.

  1. Clone a branch feat/pr9-slo do demo: git checkout feat/pr9-slo.
  2. Verifique que o CI verde rodou e que metrics/history.jsonl tem pelo menos 10 entradas (preenchido por script de seed).

Budget queimou. E agora? 3 caminhos.

Diante do burn rate em curso, SRE saudável pondera 3 respostas. Não existe "a certa": existe "a defensável diante do dado".

Ajustar o código

Burn agudo inesperado após mudança identificável: revert mais correção. Padrão saudável. É o caminho default quando há causa clara.

Ajustar o SLO

Burn sustentado com causa estrutural (hardware muda, missão muda): revisar meta com dado, NÃO com ansiedade. Vide ADR-005 como referência de revisão guiada por dado.

Aceitar a queima

Budget existe pra ser gasto. Se sobra 30% no fim do mês, talvez o SLO esteja conservador demais. Ou vocês não estão mudando o bastante.

Erro comum a evitar

Tratar SLO como SLA. SLA é externo (contrato com penalidade). SLO é interno (acordo entre dev e produto). Ajustar SLO não "engana" ninguém, desde que documentado em ADR.

Checagem 1 de 2, budget esgotado

Você define SLO de 99.9% de sucesso em 30 dias. O budget esgota no dia 28 do mês após um deploy ruim. Qual é a resposta SRE saudável?

  • Aumentar SLO pra 99.99% e prometer mais qualidade
  • Freezar deploys não-críticos até o budget recuperar; postmortem do deploy ruim; reavaliar SLO só se o padrão se repetir nos próximos meses
  • Baixar SLO pra 99% imediatamente pra não esgotar de novo
  • Ignorar, budget esgotado é problema do mês passado

Checagem 2 de 2, multi-window burn

Burn rate de 14.4x na janela de 1h, mas 0.5x na janela de 30d. Como interpretar?

  • Sistema está fora de SLO, declare incidente
  • Sistema está dentro de SLO, ignore o burn de 1h

  • Burn rate de 1h é falso positivo, monitore só por 30d
