Git hooks e secrets, a primeira barreira

Quatro hooks, Husky, lint-staged, scanner de secrets. Vocês saem da sala com isso rodando no repo.

inteli

Os quatro hooks que importam

Git tem mais de dez hooks. Na prática do dia a dia, quatro resolvem 95% dos casos. Dois rodam no cliente (laptop), dois no servidor. Todos são scripts shell comuns na pasta .git/hooks. Husky só empacota esses scripts em uma configuração versionável.

Cliente

pre-commit

Roda antes de o commit ser criado. Bloqueia se o lint quebrar ou o teste falhar. É o 80% do uso.

Cliente

commit-msg

Valida a mensagem do commit. Lugar natural do commitlint, forçando Conventional Commits.

Cliente

pre-push

Antes de enviar ao remoto. Bom para rodar a suite completa, teste de integração, coisas mais demoradas.

Servidor

pre-receive

Roda no servidor Git antes de aceitar o push. Aqui mora política: proteção de branch, regras organizacionais.

Hook é script shell, nada de mágica

Abre .git/hooks/pre-commit.sample em qualquer repositório clonado. É shell. Husky versiona esses scripts na pasta .husky/ do projeto, então toda a equipe herda o mesmo comportamento ao clonar. Sem Husky, cada dev tem o próprio hook, o que já é ter nenhum.

O trio que a Sprint usa

No repositório da Sprint, três pacotes trabalham juntos. Cada um resolve uma fatia do problema e nenhum substitui o outro. O arquivo .husky/pre-commit chama o npx lint-staged, que por sua vez consulta o package.json para saber o que rodar em cada tipo de arquivo.

Husky

Instala os hooks na pasta .husky/ e garante que o Git use eles. Configuração mora no repo, não no laptop.

lint-staged

Roda comando só nos arquivos do stage. Editou dois arquivos em cem, ele rodou lint em dois. Feedback em segundos.

commitlint

Valida a mensagem contra a regra Conventional Commits. feat:, fix:, chore:. Commit vago não passa.

// package.json, trecho do lint-staged
"lint-staged": {
  "*.{js,jsx,ts,tsx}": ["eslint --fix", "prettier --write"],
  "*.{md,json}": ["prettier --write"]
}

Ativar hook e cercar secret por dois lados

  1. Clone github.com/josercf/inteli-2026-1B-T13-ES10-S3, rode npm install. O postinstall ativa o Husky.
  2. Plante o secret: adicione AWS_SECRET_ACCESS_KEY="AKIA1234567890EXAMPLE" em um arquivo e tente git commit -m "wip". O hook deve barrar.
  3. Conserte: remova o secret, ajuste para feat: testar hook, confirme que o segundo commit passa.
  4. Rode TruffleHog standalone via Docker contra o histórico: docker run --rm -v "$PWD":/repo trufflesecurity/trufflehog:latest git file:///repo.
  5. Em dupla, compare o que o hook viu com o que o scan standalone viu. Anote uma diferença prática entre os dois.

Se o commit vago passar, seu Husky não está ativo. Rode npx husky init. Se o docker run não puxar imagem, confirme se o Docker Desktop está aberto.

Debrief A, o que quase todo mundo quebra

Toda turma tropeça nos mesmos três pontos quando ativa Husky pela primeira vez. Mapeio aqui para vocês não gastarem tempo no óbvio e pra gente discutir juntos em um minuto.

1, Hook não roda

Esqueceu npm install. Sem postinstall, o Husky não engata. Sintoma: commit passa sem mensagem de lint.

2, Lint falha sem diff

lint-staged rodou em arquivo que não está no stage. Confere se você fez git add só do arquivo que editou.

3, Secret passa por pouco

Usou string com entropia baixa, tipo abc123. TruffleHog ignora. Use o prefixo AKIA que ele reconhece.

A pergunta que fica

Se o hook roda só no laptop, um dev mal-intencionado desativa com git commit --no-verify. Por isso a barreira local é só uma das três. Na Aula 06 a gente volta para a mesma pergunta com scanner no servidor, que ninguém consegue pular.

inteli

Virtualização vs containers, a pilha importa

Antes de Docker, reprodutibilidade significava máquina virtual. Rodar outra cópia do sistema operacional inteira, com kernel próprio, pra isolar aplicação. Containers fazem o mesmo isolamento compartilhando o kernel do host. Menos gordura, boot em segundo, densidade alta no mesmo hardware.

Máquina virtual

App A
App B
Bins e libs (guest)
Guest OS
Hypervisor
Host OS
Hardware

Container

App A
App B
Bins e libs (imagem)
Docker Engine
Host OS (kernel compartilhado)
Hardware

O isolamento que o kernel faz

Containers usam recursos do próprio kernel Linux: namespaces para separar visão de processo, rede, usuário, e cgroups para limitar CPU, memória, IO. Docker Engine orquestra essas duas primitivas. No Mac e Windows rodam dentro de uma VM leve, por isso Docker Desktop precisa de virtualização habilitada.

Dockerfile, imagem, container, o ciclo inteiro

Três conceitos, três comandos, uma confusão bem comum. Dockerfile é a receita, arquivo de texto com instruções. Imagem é o artefato gerado pelo build, imutável, versionada por tag. Container é uma instância da imagem rodando, efêmero por natureza.

Mnemônico útil

Dockerfile está para imagem como código-fonte está para binário. Imagem está para container como classe está para instância. Quando o aluno confunde, é porque esqueceu qual é a etapa imutável e qual é a viva.

Ler um Dockerfile linha a linha

Esse é o Dockerfile que a gente vai usar no exercício. Dez linhas, cinco instruções distintas, multi-stage para reduzir tamanho da imagem final. Cada número corresponde a um comentário à direita.

# 1
FROM node:20-alpine AS build
# 2
WORKDIR /app
# 3
COPY package*.json ./
# 4
RUN npm ci
# 5
COPY . .
RUN npm run build

# 6
FROM node:20-alpine
WORKDIR /app
# 7
COPY --from=build /app/dist ./dist
COPY --from=build /app/node_modules ./node_modules
# 8
EXPOSE 3000
# 9
CMD ["node", "dist/app.js"]
  1. FROM, base image. Alpine tem 5 MB, Debian tem 100 MB.
  2. WORKDIR, pasta padrão dentro do container.
  3. COPY só o manifest primeiro, para cache.
  4. RUN npm ci instala dependências de forma determinística.
  5. COPY . . traz o código. Ordem importa para cache.
  6. Segunda FROM, stage final, sem dev dependencies.
  7. Pega só o dist do stage anterior.
  8. EXPOSE, documenta a porta, não abre nada.
  9. CMD, comando padrão quando o container sobe.

Dockerfile, três erros que toda primeira imagem comete

Errar aqui é parte do processo, por isso os três pontos abaixo aparecem em praticamente toda revisão de primeiro Dockerfile. Quem já sabe disso pula uma viagem inteira de "por que minha imagem tem 1 GB".

1, Ordem das camadas

Copiar código antes do manifest invalida o cache de dependências a cada commit. COPY package*.json primeiro, npm ci, depois COPY . .. Economiza minutos por build.

2, Multi-stage build

Imagem de build tem compilador, node_modules de dev, cache. Imagem final não precisa de nada disso. Dois FROM no mesmo Dockerfile reduzem de 900 MB para 80 MB.

3, .dockerignore

Sem ele, o COPY . . empacota node_modules, .git, coverage, fotos. Imagem infla, secret em .env vai junto. Três linhas resolvem 90% do problema.

Teste rápido

Rode docker history <imagem>. Cada linha mostra o tamanho da camada e o comando que a criou. Se tem camada de 300 MB vindo de um COPY . ., o seu .dockerignore está pedindo socorro.

Debrief B, o que a imagem gerada contém

A pergunta que separa quem entendeu Dockerfile de quem só copiou é: o que está dentro da imagem que eu acabei de gerar? Quatro observações que quase sempre aparecem em debrief.

Tamanho fala

Imagem com 700 MB normalmente tem dev dependencies ou base Debian. Multi-stage e Alpine derrubam para 80 MB. Meça antes de otimizar.

Cache é ouro

Build que leva 3 min na primeira vez deve levar 10 segundos no segundo se só o código mudou. Se levar 3 min sempre, ordem das camadas está errada.

Imagem não é VM

Container não tem systemd, cron, ssh. Roda um processo principal e morre. Se você está pensando "como entro no container e mexo", é sinal de virar código.

Pergunta de bolso

Se amanhã eu deletar o seu laptop, a imagem que você gerou roda igual em outra máquina? Se a resposta for "depende", a reprodutibilidade ainda não chegou. Dockerfile bem feito tira o depende.

inteli

Registry, onde a imagem vai morar (versão curta)

Antes de escanear, uma palavra sobre destino. Registry é servidor de artefato com namespace, autenticação e tag. docker push envia, docker pull traz. Três opções dominam o mercado, cada uma com um trade-off claro.

Docker Hub

Padrão de fato para imagens públicas. Privado paga, rate limit é real. Origem dos trufflesecurity/trufflehog, aquasec/trivy e sonarqube que a gente usa hoje.

GHCR e GitLab Registry

Embutidos no próprio GitHub/GitLab. Permissão herdada do repo, pipeline publica direto. Escolha natural quando o repo já está lá.

ECR, ACR, Artifact Registry

Registry do cloud provider, privado por padrão, integra com IAM, scanner embutido. Opção óbvia quando o deploy vai para a mesma nuvem.

Regra de ouro, ainda mais agora

Nunca rode :latest em produção. Tags semânticas (academic-tracker:1.4.2) ou digest SHA garantem que a imagem que o Trivy escaneou é a mesma que vai subir. Sem isso, a análise estática é gentileza.

Hands-on C, em dupla, 15 min

Subir SonarQube e escanear o academic-tracker

  1. Na raiz do academic-tracker, rode npm run sonar:up. Espere o container do Sonar reportar healthy (~30 s).
  2. Em outro terminal, dispare npm run sonar:scan. O scanner empacota o código, manda para localhost:9000, espera o relatório.
  3. Abra http://localhost:9000, login admin/admin, troque a senha. Entre no projeto academic-tracker.
  4. Identifique um Blocker ou Critical que não tinha aparecido só lendo o diff. Anote arquivo, regra e por que importa.
  5. Antes de derrubar, rode npm run sonar:down. Tire um print do painel com o Quality Gate visível e cole no entregável.

Se o scanner falhar com Cannot connect, o Sonar ainda está subindo. Espere mais 20 s. Se o painel ficar vazio, o scan terminou mas o relatório não foi publicado, confira a saída do passo 2.

Trivy, varrendo a imagem que vocês acabaram de gerar

A imagem do Bloco 2 carrega três superfícies de risco: o código, as dependências do package.json e a base image (node:20-alpine). Trivy varre as três de uma só vez, casando com a base de CVEs pública. Roda em container, não precisa instalar nada.

# Escanear a imagem gerada no Bloco 2 docker run --rm \ -v /var/run/docker.sock:/var/run/docker.sock \ aquasec/trivy:latest image academic-tracker:dev # Filtrar só CRITICAL e HIGH para triagem rápida docker run --rm \ -v /var/run/docker.sock:/var/run/docker.sock \ aquasec/trivy:latest image \ --severity CRITICAL,HIGH academic-tracker:dev

Checklist antes do push, para grudar no monitor

Seis linhas que a equipe madura roda antes de git push sem nem pensar. Os quatro primeiros são gratuitos (hook decide tudo). Os dois últimos custam ~2 min cada, e são a diferença entre "build verde" e "build verde, sem CVE crítica".

1, Lint

ESLint e Prettier sem warning nos arquivos tocados.

2, Teste

Unit verdes no diff, integração se afeta rota.

3, Commit

Mensagem em Conventional, validada por commitlint.

4, Secret

TruffleHog (hook + docker run) sem achado.

5, Sonar

Quality Gate verde em localhost:9000.

6, Trivy

Imagem sem CRITICAL aberto na severidade.

A regra do carrinho

Pipeline que quebra em 5 ou 6 quando 1-4 passaram é pista de que o ambiente local divergiu do runner. Container bem feito torna esse caso raro. Pipeline que quebra em 1, 2 ou 3 é sinal de que o hook não rodou, ou o dev passou com --no-verify. Nos dois casos, a conversa é outra.
