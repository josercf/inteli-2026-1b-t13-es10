Hook: mesma feature, duas formas

Trechos reais de tools/quality_gates.py do demo. Esquerda, como está hoje. Direita, refatorado com tipo + polimorfismo. A feature é IDÊNTICA.

Antes, procedural

def check_gate(name, actual, threshold, operator):
    if operator == ">=":
        passed = actual >= threshold
    elif operator == "<=":
        passed = actual <= threshold
    elif operator == "==":
        passed = actual == threshold
    elif operator == "<":
        passed = actual < threshold
    elif operator == ">":
        passed = actual > threshold
    else:
        raise ValueError(operator)
    return {
        "name": name,
        "passed": passed,
        "actual": actual,
        "threshold": threshold,
    }

Depois, polimorfismo

class Gate(ABC):
    def __init__(self, name, threshold):
        self.name = name
        self.threshold = threshold

    def evaluate(self, actual) -> GateResult:
        return GateResult(
            name=self.name,
            passed=self._compare(actual),
            actual=actual,
            threshold=self.threshold,
        )

    @abstractmethod
    def _compare(self, actual): ...

class MinThresholdGate(Gate):
    def _compare(self, actual):
        return actual >= self.threshold

class MaxThresholdGate(Gate):
    def _compare(self, actual):
        return actual <= self.threshold

Heurísticas do bom código sobre o demo

5 heurísticas. Aplicadas a trechos REAIS de tools/ e libs/ do inteli-px4-cicd-demo. Vocês vão usar nas próximas 2h.

inteli

5 heurísticas, com exemplo no demo

1. Nomes que dizem intenção

def x(d, t): vs def evaluate_gate(metrics, thresholds):. Tipo + papel no nome. Aplicado: tools/extract_metrics.py tem 3 funções com nome OK, 2 com nome opaco.

2. Funções curtas, um trabalho

Limite mental: cabe em 1 tela sem rolar (~30 linhas). quality_gates.check_coverage() faz: ler XML, parsear, comparar, formatar. 4 trabalhos. Quebrar.

3. Eliminar ramificação tipo-baseada

If/elif sobre "tipo de operação" = polimorfismo escondido. check_gate(operator='>=') é um dispatch manual.

4. Limitar acoplamento

Função que recebe dict opaco + 4 strings = consumidor precisa saber estrutura interna. Receber objeto tipado = compilador valida.

5. Testabilidade no design

Função que abre arquivo + parsa + compara = só testa com arquivo real. Função que recebe dados já parseados + retorna resultado = unit test puro.

Heurística não é regra. Heurística é direção. Romper a regra com motivo escrito é melhor que segui-la sem entender.

Antes, quality_gates.py procedural

# tools/quality_gates.py (estado atual)

def check_coverage(xml_path, threshold):
    tree = ET.parse(xml_path)
    line_rate = float(tree.getroot().attrib["line-rate"])
    passed = line_rate >= threshold
    return {"name": "coverage", "passed": passed,
            "actual": line_rate, "threshold": threshold}

def check_mission_metrics(json_path, thresholds):
    data = json.loads(Path(json_path).read_text())
    rms = data["trajectory_rms_m"]
    passed = rms <= thresholds["max_rms_m"]
    return {"name": "mission_rms", "passed": passed,
            "actual": rms, "threshold": thresholds["max_rms_m"]}

def check_sonar(report_path, threshold):
    data = json.loads(Path(report_path).read_text())
    bugs = data["bugs"]
    passed = bugs <= threshold
    return {"name": "sonar_bugs", "passed": passed,
            "actual": bugs, "threshold": threshold}

# E quando vier o 4º? E o 5º? Copia-cola de novo.

Sintomas

  1. 4 funções com mesma estrutura: lê fonte, parseia, compara, retorna dict.
  2. Adicionar o 5º gate = copiar-colar a 5ª vez. Cada cópia é uma chance de divergir o formato do dict.
  3. Tratamento de erro (arquivo ausente, JSON mal-formado) terá que ser repetido em cada função.
  4. Teste unitário precisa de arquivo real em disco. Não dá pra mockar só a leitura.
  5. Forma é estável, conteúdo varia. É o sinal clássico de template method.

Depois, Gate como template method

from abc import ABC, abstractmethod
from dataclasses import dataclass

@dataclass
class GateResult:
    name: str
    passed: bool
    actual: float | None
    threshold: float
    message: str

class Gate(ABC):
    def __init__(self, name: str, threshold: float):
        self.name = name
        self.threshold = threshold

    def evaluate(self) -> GateResult:
        try:
            actual = self._read_actual()
        except FileNotFoundError as e:
            return GateResult(self.name, False, None,
                              self.threshold, str(e))
        passed = self._compare(actual)
        return GateResult(self.name, passed, actual,
                          self.threshold,
                          self._format(actual, passed))

    @abstractmethod
    def _read_actual(self) -> float: ...
    @abstractmethod
    def _compare(self, actual: float) -> bool: ...
    @abstractmethod
    def _format(self, actual: float, passed: bool) -> str: ...

class CoverageGate(Gate):
    def __init__(self, threshold: float, path: Path):
        super().__init__("coverage.min_line_coverage", threshold)
        self._path = path
    def _read_actual(self): return _parse_coverage_xml(self._path)
    def _compare(self, actual): return actual >= self.threshold
    def _format(self, actual, passed):
        op = "≥" if passed else "<"
        return f"line coverage {actual:.1%} {op} {self.threshold:.0%}"

Anatomia

  1. Template method: evaluate() é o algoritmo geral. Subclasses preenchem os 3 vazios.
  2. Adicionar SonarGate = 1 classe, 0 if novos.
  3. Erros de leitura centralizados no método pai. Toda subclasse herda o tratamento.
  4. GateResult tipado: dataclass documenta a interface. Consumidor não precisa adivinhar keys.
  5. Testabilidade: mock só _read_actual, teste lógica de compare/format sem disco.

Trade-offs honestos do refactor

OOP não é grátis. Antes de aplicar em todo módulo, encarar o que se ganha e o que se perde.

Ganhos

  • Adicionar gate = 1 classe nova, sem tocar no resto.
  • Erros de IO centralizados no método pai.
  • Tipo do actual documenta intenção.
  • Testes unitários por gate (mock só do _read_actual).
  • Pipeline de execução genérico: for g in gates: g.evaluate().

Custos

  • Mais arquivos pra navegar.
  • 1 classe pra 1 uso = overengineer (não vale a pena se nunca crescer).
  • Herança como contrato escondido, quem implementa Gate deve preencher os 3 abstratos sem esquecer.
  • Debug exige seguir o método pai + subclasse (2 saltos mentais).

Critério

OOP entra quando tem ≥3 variações com mesma forma. 2 variações = duplicação aceitável. 1 variação = função simples. Não OOP por OOP.

Refactor Dojo, critério de aceitação

5 critérios que separam refactor responsável de "mexer pra ver no que dá". Sua dupla precisa atender os 5 pra entregar.

  1. Diff cabe em até 100 linhas (limite mental do review).
  2. Pelo menos 1 das 5 heurísticas do Bloco 2 é endereçada (escreva qual no commit).
  3. Testes existentes passam sem modificação (se mudou API, ajuste o teste em commit separado).
  4. README do trecho ganha 3 linhas explicando o "antes/depois" e por quê.
  5. Pelo menos 1 trecho NÃO refatorado: o que vocês decidiram deixar e por quê (decisão consciente > limpeza compulsiva).

Dúvida frequente: "isso vale a pena ser feito agora?", se a resposta é "pode esperar mais um ciclo", deixa pra próxima. Refactor com pressa quebra mais que conserta.

Code Review Cruzado: revise outra dupla com 5 perguntas

Troca de diffs entre duplas. 15min revisando + 5min de feedback ao vivo. Não é nota, é conversa técnica.

inteli

Checklist de review, 5 perguntas

1. Motivo está claro?

Você entende o motivo do diff sem perguntar? Se a justificativa não está clara em commit ou README, é sinal de motivo fraco.

2. Nome novo > nome velho?

O nome novo diz mais que o velho? Se você precisa ler o corpo da função pra entender, o nome falhou.

3. Testes ainda fazem sentido?

Refactor sem quebrar teste = bom. Refactor mudando expectativa = scope creep. Pergunte o porquê da mudança no teste.

4. Você adicionaria essa abstração?

Honestidade: às vezes a resposta é "não, mas o autor tem motivo válido". Pergunte ao autor antes de bloquear.

5. Quer copiar pro seu código?

Tem algo aqui que você quer copiar pro seu próprio código? Review como aprendizado mútuo, não só correção.

Tom importa

"Por que essa escolha?" > "isso está errado". Code review é técnica social tanto quanto técnica.

Checagem 1 de 2, quando aplicar polimorfismo

Você está refatorando um módulo com 2 variações similares (process_csv e process_json). Cada um tem 30 linhas, 80% iguais. O caminho mais RESPONSÁVEL agora é:

  • Criar classe abstrata Processor com process_csv e process_json como subclasses, antecipando JSON-LD, YAML, XML no futuro
  • Extrair função compartilhada para a parte comum, deixar 2 funções (process_csv, process_json) usando ela. Polimorfismo só quando aparecer a 3ª variação
  • Deixar duplicado, comentar "TODO: refatorar quando virar 3"
  • Mover ambos para um único process(data, format) com if/elif no operador

Checklist de craft pessoal

6 hábitos que separam quem entrega de quem entrega bem. Pra levar pra além do módulo.

1. Leitura ativa semanal

1 PR open-source bem feito ou 1 capítulo de Clean Code, com 1 anotação.

2. Refactor sem feature

Pelo menos 1 PR por sprint que só limpa código. Sem feature nova. Sem permissão especial.

3. Commit como narrativa

Mensagem explica o porquê. Diffs caem em ≤200 linhas. Quem revisar entende sem call.

4. Review como aprendizado

Pelo menos 1 pergunta por review (não só sugestão). Aprenda do diff alheio.

5. Decisão escrita

ADR ou doc para qualquer escolha não-trivial. Decisão sem doc vira lenda em 3 meses.

6. Prática deliberada

1 kata, 1 projeto paralelo, 1 stack nova por trimestre. Habilidade decai sem uso.
