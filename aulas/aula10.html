Bloco 1, 20 min

Quality gate como contrato — hierarquia de checks

Métrica que ninguém respeita é decoração. Gate é regra. Hoje atravessamos essa fronteira.

inteli

Métrica informativa vs. quality gate

Diferença não é técnica — é política. Mesmo número, mesma extração, mesma tabela. O que muda: a esteira respeita esse número.

Métrica informativa (até PR #3)

  • Aparece no comentário do PR
  • Reviewer pode usar pra decidir
  • Merge não é bloqueado se regredir
  • Em prática: ninguém lê depois da 2ª semana

Quality gate (PR #4)

  • Threshold versionado em quality_gates.yaml
  • Pipeline falha + GitHub bloqueia botão "Merge"
  • Mudança do threshold passa por PR + revisão
  • Decisão fica registrada (commit + ADR)

A inversão silenciosa

O reviewer não precisa mais "checar se passou no padrão". O pipeline faz. Reviewer foca no design da mudança. Code review fica mais barato e mais profundo simultaneamente.

A hierarquia de checks num pipeline maduro

Não é "quanto mais teste melhor" — é "qual classe de erro cada nível pega". Cada um custa mais e pega coisas que o anterior não viu.

1. Lint + format

Sintaxe, estilo, tipos óbvios. Custo: <5s. Pega 30% dos bugs simples (typo, import errado).

2. Unit tests

Lógica isolada de função pura. Custo: <1min. Pega regressão de algoritmo. Cobertura mensurável.

3. SAST (Sonar)

Análise estática de segurança + qualidade. Custo: ~30s. Pega code smells, vulnerabilities, complexity.

4. Integration tests

Sistema rodando (SITL). Custo: ~8min. Pega bugs de composição, timing, configuração.

5. Mission metrics

KPIs do sistema em execução. Custo: já calculado no #4. Pega regressão de performance.

6. Invariantes físicos / Quality gates

Regras absolutas + thresholds versionados. Custo: ~10s pra avaliar. Pega tudo que escapou.

Bloco 2, 20 min

Sequencial fail-fast: paralelo informativo → gate-driven

Quando paralelo é melhor, quando sequencial é melhor, e por que migramos agora.

inteli

Paralelo (PRs #1-#3) vs sequencial (PR #4)

A mesma chain de checks, ordem de execução diferente. Trade-off real:

Paralelo (informativo)

  • Lint + Sonar + Build rodam simultaneamente
  • Feedback rápido: vê 3 erros possíveis em <1min
  • Mesmo se lint falha, build cold (~25min) já gastou recurso
  • Faz sentido enquanto gates são informativos

Sequencial fail-fast

  • Lint → Sonar → Build → Mission → Gates em cadeia
  • Lint falha? Sonar nem roda. Sonar falha? Build nem roda. Economia.
  • ~30s mais lento quando tudo passa (custo do feedback acumulado)
  • Faz sentido quando gates são obrigatórios: não vale gastar runner se já tá falhando

Por que migramos AGORA

PR #1-#3 priorizou feedback (gate informativo, paralelismo ajuda). PR #4 prioriza economia + decisão (gate obrigatório — se lint falha, nada do resto importa, e gastar runner self-hosted por 25min é desperdício direto).

tools/quality_gates.py — o avaliador

def evaluate(gates_yaml, metrics_json, coverage_xml,
             sonar_host, sonar_token, sonar_project_key):
    config = yaml.safe_load(gates_yaml.read_text())
    results = []

    # 1. Coverage
    cov_threshold = config["coverage"]["min_line_coverage"]
    results.append(check_coverage(coverage_xml, cov_threshold))

    # 2. Mission metrics
    results.extend(
        check_mission_metrics(metrics_json,
                              config["mission_metrics"])
    )

    # 3. Sonar (consulta API)
    results.append(
        check_sonar(sonar_host, sonar_token,
                    sonar_project_key,
                    require=config["sonar"]["require_quality_gate_passed"])
    )

    all_passed = all(r.passed for r in results)
    return GatesReport(all_passed=all_passed, results=results, ...)

3 fontes, 1 resultado

  1. coverage.xml: gerado pelo pytest-cov; parser Cobertura standard.
  2. metrics.json: gerado pelo tools/extract_metrics.py (PR #2).
  3. Sonar API: /api/qualitygates/project_status — devolve OK ou ERROR.
  4. exit code: 0 se todos passam, !=0 se qualquer um falha.
  5. 11 testes unit: cobrem cada check em isolado + orquestração.

Job quality-gates no ci.yml

quality-gates:
  needs: mission-test    # ÚLTIMO da chain
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-python@v5
      with:
        python-version: "3.11"
    - run: pip install -r requirements-dev.txt

    - uses: actions/download-artifact@v4
      with: { name: coverage-xml }
    - uses: actions/download-artifact@v4
      with: { name: mission-metrics, path: reports/ }

    - name: Evaluate quality gates
      env:
        SONAR_HOST_URL: ${{ secrets.SONAR_HOST_URL }}
        SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
        SONAR_PROJECT_KEY: ${{ secrets.SONAR_PROJECT_KEY }}
      run: |
        python -m tools.quality_gates \
          --gates quality_gates.yaml \
          --metrics reports/metrics.json \
          --coverage coverage.xml \
          --output reports/quality_gates_result.json

Por que esse job vem por último

  1. needs: mission-test: precisa do metrics.json gerado.
  2. artifacts consumidos: coverage do job 1, mission do job 4.
  3. Sonar via secrets: pipeline consulta Sonar do instrutor via token.
  4. output JSON: vira artifact próprio + comentário no PR (step seguinte).
  5. exit != 0 bloqueia merge: GitHub branch protection deve marcar quality-gates como required check.

Pausa humana antes do veredito — manual-approval

Robôs fizeram a parte deles (lint, SAST, build, missão). Antes do quality-gates automático bater o martelo, pipeline trava num gate humano. Pedagógico: força a turma a parar no resumo de métricas e discutir o que está olhando.

manual-approval:
  needs: mission-test
  if: github.event_name == 'pull_request'   # só em PR
  runs-on: ubuntu-latest
  environment: quality-review               # ← required reviewers
  timeout-minutes: 60
  steps:
    - name: Registrar aprovação
      run: echo "Aprovado por @${{ github.actor }}"

quality-gates:
  needs: [mission-test, manual-approval]
  if: ${{ always()
          && needs.mission-test.result == 'success'
          && (needs.manual-approval.result == 'success'
              || needs.manual-approval.result == 'skipped') }}

Mecânica

  1. Environment quality-review: feature nativa do GitHub. Settings → Environments → required reviewers: josercf, hermanopoj (qualquer um aprova).
  2. Pipeline trava: na aba Actions aparece "Review pending deployments". Aprova ali ao vivo.
  3. Só em PR: push direto pra main pula esse job. quality-gates roda quando approval é success OU skipped.
  4. Timeout 60min: se ninguém aprovar, job falha e libera o runner. Não fica pendurado.
  5. ADR-008 registra o trade-off: clareza pedagógica + auditoria humana × latência adicional.

Release + promote — rollback via re-tag

Como sair do "PR mergeado" pra "binário voando" — com rollback de 30 segundos.

inteli

release.yml — quando uma tag git vira firmware

Até agora o pipeline produzia imagem SITL (pra simulador). Pra deployar em drone real, precisamos do binário hardware — saída diferente do mesmo código.

Trigger

on: push: tags: ['v*']. Quando alguém faz git tag v0.1.0 && git push --tags, o workflow dispara.

Build hardware

make px4_fmu-v6x_default — diferente de px4_sitl_default. Produz binário pra Pixhawk físico.

GitHub Release

Anexa .px4 (flasheável) + .sha256 (checksum). Vira "download oficial" da versão.

Decisão importante

Só dá pra criar tag v* de um commit que está em main. main só recebe merge se quality gates passaram (PR #4). Logo: toda release publicada passou pelos gates. Cadeia inquebrável.

promote.yml — dev → staging → prod

on:
  workflow_dispatch:    # manual
    inputs:
      source_tag:       # ex.: dev-abc123
        required: true
      target_env:
        type: choice
        options: [staging, prod]

jobs:
  promote:
    runs-on: ubuntu-latest
    environment: ${{ inputs.target_env }}  # APROVAÇÃO HUMANA
    steps:
      - name: Promote (retag)
        run: |
          python -m tools.promote_release \
            --image ghcr.io/josercf/px4-sitl \
            --from ${{ inputs.source_tag }} \
            --to ${{ steps.tag.outputs.target_tag }}

Mecânica

  1. workflow_dispatch: humano vai em Actions → Run workflow.
  2. environment: staging: GitHub pausa pra aprovação dos reviewers configurados em Settings → Environments.
  3. promote_release.py: docker pull SRC; docker tag SRC DST; docker push DST. Mesma imagem byte-a-byte.
  4. Custo: ~10s por promoção. Não é build.
  5. Rollback: re-tag inverso — em <30s a imagem antiga volta a responder pela tag prod-.

Rollback em 30 segundos

Drone caiu em campo. Suspeita: regressão na versão prod-abc123. Procedimento de rollback documentado:

# 1. Identifica a versão anterior que estava em prod
gh release list --limit 5

# 2. Re-tag GHCR: prod-OLD aponta pra SHA antigo
python -m tools.promote_release \
  --image ghcr.io/josercf/px4-sitl \
  --from prod-old_sha \
  --to prod-CURRENT

# 3. Pipeline de OTA pega prod-CURRENT na próxima janela
#    (ou força via gateway/OpenChoreo)

Por que isso funciona

A imagem velha NUNCA foi deletada — só apontamos o "ponteiro" prod-CURRENT pra ela. Rollback é gratuito porque preservamos histórico no registry. ADR-004 explicita essa estratégia.

Checagem 1 de 2, gate vs threshold

Sua equipe descobriu que max_acceleration_m_s2 está sempre próximo do limite (14.8 de 15). Cada novo PR passa por um fio. Qual é a abordagem mais saudável?

  • Deletar o gate — está virando ruído
  • Manter threshold, mas investigar a causa raiz (provavelmente sintonia agressiva do controlador)
  • Trocar gate por warning informativo
