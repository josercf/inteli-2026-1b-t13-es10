Os 8 minutos do mission-test, quebrados

Lendo o log do PR #4, run #21, com actions/timing-summary: o tempo NÃO está distribuído como achávamos.

1. Pull SITL image

~95s. GHCR puxa a imagem do PX4-SITL (~1.2GB) toda vez. Sem cache de layer.

2. Cold-start SITL

~70s. PX4 inicia, Gazebo carrega modelo do x500, sensores se calibram. Toda missão paga isso de novo.

3. MAVSDK handshake

~40s. Espera "connection state == CONNECTED". Hoje via await asyncio.sleep(40) conservador.

4. Sleep-based waits no test

~85s acumulados. await asyncio.sleep(N) em 7 pontos do run_mission.py. Cada um é "espera N segundos pra ter certeza".

5. Execução real da missão

~95s. Voo: takeoff, 4 waypoints, land. Isso é a única parte "essencial".

6. Coleta + parse de ULog

~25s. Download do log, pyulog extrai KPIs.

~410s + overhead = ~7-8min. Apenas ~95s (23%) é "fazer o voo". Os outros 77% são setup recuperável.

Top-3 gargalos e por onde atacar

Cada gargalo tem uma camada certa. Aplicar técnica errada na camada errada = ganho marginal ou flake. Diagnóstico antes de solução:

Gargalo

  • Pull SITL image (95s) — repete por job, mesmo SHA
  • Cold-start SITL (70s) — repete por TESTE (cada test_*.py reinicia)
  • Sleep-based waits (85s) — folga conservadora em estado já pronto

Camada que resolve

  • Cache do CI (Bloco 2): buildx + GHCR-as-cache
  • Fixtures scope="session" (Bloco 3): 1 SITL pra toda a suite
  • await condition() em vez de sleep() (Bloco 3): poll real

A pergunta da escolha

"Esse custo é por commit? Por job? Por teste? Por execução?" — a resposta dita a camada. Cache só ajuda em coisa idêntica à execução anterior. Fixture session só ajuda em coisa compartilhável entre testes na MESMA execução.

Bloco 2, 25 min

4 camadas de cache no CI

Pip, Sonar, Buildx layers, submódulo PX4. Cada uma resolve um custo recorrente diferente.

inteli

Visão geral: 4 chaves, 4 custos diferentes

Cada chave de cache responde a uma pergunta: "o que torna esse trabalho idêntico ao da última execução?". Errar a chave = cache nunca hita OU hita quando não devia (correctness break).

1. pip cache

Chave: hashFiles('requirements*.txt'). Pra reusar wheels Python entre runs sem reinstalar. Economia esperada: ~25s por job python-quality.

2. sonar cache

Chave: hashFiles('sonar-project.properties') + branch. Pra evitar reanalisar arquivos não alterados. Economia: ~20s por job sonar-scan.

3. buildx layer cache

Chave: gerenciada pelo Docker via type=gha. Pra reusar layers da imagem SITL quando Dockerfile não mudou. Economia: ~90s no pull + build (maior ganho).

4. PX4 submódulo cache

Chave: SHA do submódulo (saída de git submodule status). Submódulo PX4 raramente muda — clonar 200MB toda vez é desperdício. Economia: ~15s.

Soma teórica: ~150s economizados por job, ~95s no maior (mission-test via buildx). Ganho real depende da taxa de hit — que é o tema do próximo slide.

Camadas 1 e 2: pip + sonar

- uses: actions/cache@v4
  with:
    path: ~/.cache/pip
    key: pip-${{ runner.os }}-${{ hashFiles('requirements*.txt') }}
    restore-keys: |
      pip-${{ runner.os }}-

- uses: actions/cache@v4
  with:
    path: ~/.sonar/cache
    key: sonar-${{ hashFiles('sonar-project.properties') }}-${{ github.ref_name }}
    restore-keys: |
      sonar-${{ hashFiles('sonar-project.properties') }}-
      sonar-

Anatomia da chave

  1. hashFiles garante invalidação quando deps mudam.
  2. restore-keys permite fallback parcial: "se não tem cache exato, usa o mais recente da família" — partial hit é melhor que miss total.
  3. branch no sonar isola por PR: análise de branch X não polui Y.
  4. runner.os separa Linux/Mac/Win — pip cache não é portável.
  5. Cuidado: cache de pip NÃO instala. Sempre seguido de pip install (que vira no-op se hit).

Camada 3: buildx layer cache (o maior ganho)

- uses: docker/setup-buildx-action@v3

- uses: docker/build-push-action@v6
  with:
    context: .
    file: docker/Dockerfile.sitl
    push: true
    tags: ghcr.io/josercf/px4-sitl:${{ github.sha }}
    cache-from: type=gha,scope=sitl
    cache-to:   type=gha,scope=sitl,mode=max

Por que type=gha é a escolha

  1. type=gha: usa o cache nativo do GitHub Actions (~10GB grátis por repo).
  2. scope=sitl: separa de outras imagens. Múltiplos workflows não colidem.
  3. mode=max: cacheia todos os layers, não só os finais. Custo: cache maior.
  4. Layer determinístico: cada FROM/COPY/RUN é uma chave. Layer só rebuilda quando o COPY ou comando muda.
  5. Layer compartilhado entre PRs: PR #5 e PR #6 abertos hoje reaproveitam layers do main. Cache amortiza pra toda a turma.

Camada 4: cache do submódulo PX4

- name: Get PX4 submodule SHA
  id: px4-sha
  run: |
    SHA=$(git submodule status PX4-Autopilot | awk '{print $1}' | tr -d '+-')
    echo "sha=$SHA" >> $GITHUB_OUTPUT

- uses: actions/cache@v4
  with:
    path: PX4-Autopilot
    key: px4-submodule-${{ steps.px4-sha.outputs.sha }}

- name: Init submodule if cache miss
  if: steps.cache.outputs.cache-hit != 'true'
  run: |
    git submodule update --init --recursive --depth 1 PX4-Autopilot

Truques desta camada

  1. Chave = SHA do submódulo, não da branch. Submódulo só muda quando ADR-001 manda — raro.
  2. Sem restore-keys: queremos hit exato ou clone limpo (PX4 parcial = compila errado).
  3. Init condicional: git submodule update só roda se cache miss. Economia ~15s na maioria dos PRs.
  4. depth 1: shallow clone, suficiente pra build do firmware.
  5. ADR-008 documenta: cache de submódulo é o único onde correctness > speedup — invalidação errada quebra build em tempo de execução.

inteli

conftest.py: uma SITL pra toda a suite

# tests/sitl/conftest.py

@pytest.fixture(scope="session")
def sitl_process():
    """Sobe PX4 + Gazebo uma vez por suite. Custo: ~70s, pago uma vez."""
    proc = launch_sitl(headless=True, model="x500")
    wait_for_log_pattern(proc, "Ready for takeoff")
    yield proc
    teardown_sitl(proc)

@pytest.fixture(scope="session")
async def drone(sitl_process):
    """Conecta MAVSDK uma vez. Reutilizado por todos os tests da suite."""
    d = System()
    await d.connect(system_address="udp://:14540")
    async for state in d.core.connection_state():
        if state.is_connected:
            break
    yield d

@pytest.fixture(scope="function")
async def armed_drone(drone):
    """Cada teste arma+desarma — estado isolado, conexão reaproveitada."""
    await drone.action.arm()
    yield drone
    if await is_armed(drone):
        await drone.action.disarm()

As 2 escolhas críticas

  1. scope="session" em sitl_process e drone: pagam o setup 1x. Antes do PR #7 isso era scope="function" — 70s por teste.
  2. scope="function" em armed_drone: estado mutável (armed) deve isolar por teste.
  3. Teardown sempre: yield + cleanup garante que crash em meio à suite não vaza estado.
  4. Cuidado de isolamento: testes que poluem estado físico do drone (ex.: home position) ainda precisam reset entre runs.
  5. ADR-008 documenta: quando function-scope é não-negociável (mutação de estado), session-scope quebra correctness.

await condition() em vez de sleep()

# ❌ Antes: tools/run_mission.py
await drone.action.arm()
await asyncio.sleep(5)   # "tempo conservador pra estar armado"

await drone.action.takeoff()
await asyncio.sleep(15)  # "tempo pra subir a 10m"

await drone.mission.upload_mission(mission_plan)
await asyncio.sleep(3)

# ✅ Depois (PR #7):
await drone.action.arm()
await wait_until(lambda: is_armed(drone), timeout=10)
# Sai quando estado real == True. Tempo típico: ~0.4s.

await drone.action.takeoff()
await wait_until(
    lambda: altitude_above(drone, target=9.5),
    timeout=30
)
# Sai quando altitude >= 9.5m. Tempo típico: ~6s.

await drone.mission.upload_mission(mission_plan)
await wait_until(lambda: mission_upload_complete(drone), timeout=10)

Por que sleep é dívida técnica

  1. Sleep é "pior caso fixo": pagamos a folga TODA vez, mesmo quando o sistema convergiu em 0.4s.
  2. Sleep mente quando o sistema atrasa: se algo travar além do esperado, sleep passa direto e quebra silencioso.
  3. Poll real lê estado verdadeiro: is_armed(), altitude_above(), mission_complete().
  4. Timeout protege contra hang: se condição nunca for atingida, falha com erro claro em vez de pendurar.
  5. 5 sleeps removidos no PR #7: economia acumulada ~85s por mission-test.

pytest-xdist: missões em paralelo

# requirements-dev.txt:
# pytest-xdist

# tests/sitl/test_mission_invariants.py:
@pytest.mark.parametrize("mission,max_rms_m", [
    ("square_50m.yaml",   2.0),
    ("triangle_30m.yaml", 1.5),
    ("zigzag_80m.yaml",   2.5),
])
async def test_trajectory_within_rms(armed_drone, mission, max_rms_m):
    plan = load_mission(f"missions/{mission}")
    log = await run_mission(armed_drone, plan)
    assert trajectory_rms(log) <= max_rms_m

# .github/workflows/ci.yml (job mission-test):
- name: Run mission tests in parallel
  run: pytest tests/sitl -n 3 --dist=loadgroup

Paralelizar sem flake

  1. 3 missões parametrizadas em vez de 3 testes copy-paste. DRY + xdist enxerga 3 nós.
  2. -n 3: 3 workers. CPU do runner é o limite.
  3. --dist=loadgroup: testes do mesmo módulo ficam juntos (compartilham fixture session). Sem isso, cada worker abriria sua SITL — flake garantido.
  4. Cuidado MAVLink port: cada SITL escuta porta 14540. Em paralelo cada worker precisa de instância isolada. Fixture do PR #7 aloca porta dinâmica.
  5. Ganho real: 3 missões serial ~285s → paralelo ~110s. Economia: ~175s.

Checklist de pipeline performant

6 sinais de que vocês têm performance sob controle. Não é "pipeline rápido", é "pipeline com custo medido e cada decisão justificada".

1. Profile, não palpite

Você sabe os top-3 gargalos do seu mission-test (em segundos, não "parece lento").

2. 4 camadas de cache

pip + sonar + buildx + submódulo. Cada chave invalida quando deve, e só quando deve.

3. Hit ratio monitorado

Log do CI mostra "Cache hit ✓" pra 4 chaves no caso comum. PR que muda requirements vê pip miss, restantes hit.

4. Fixtures session-scope

O caro (SITL boot, conexão MAVSDK) paga 1x por suite. Função-scope só onde estado muda.

5. Zero sleep() em path crítico

Toda espera é await condition() com timeout. Folga conservadora foi embora.

6. docs/performance.md

Tabela antes/depois versionada. Próximo speedup tem baseline pra comparar.

PR #7 entrega os 6. Quem fizer hands-on completo + identificar uma 7ª camada (ex.: cache do Sonar binário, cache de wheel customizado) ganha ponto extra.
